PYROET OS 1.0.0 -- INSTALL NOTES (CC:Tweaked)
=============================================
Plain ASCII on purpose: readable on a CC:Tweaked terminal too. All paths are
in-game paths.

0. PREREQUISITES
- CC:Tweaked or a compatible CraftOS on a Pocket Computer (26x20 target;
  smaller screens degrade to one status line).
- 1,000,000 B computer storage (default quota). Before a system update keep
  about 601,778 B free: image 401,778 B + backup cap 200,000 B.
- Release archive pyroet-os-v1.0.0.zip (pyroet-os/ tree plus LICENSE).
  tests/ and tools/ are NOT shipped (development material).
- A modem for networking or a rednet install (the modem is auto-discovered;
  pocket computers have no sides). Without one the system still boots; net
  reports degraded.
- /recovery/*.lua is optional for booting but is the only rescue path.

1. ARCHIVE -> TARGET PATHS
Copy each member with a prefix swap:
  pyroet-os/startup.lua            -> /startup.lua
  pyroet-os/system/startup.lua     -> /system/startup.lua
  pyroet-os/system/boot.lua        -> /system/boot.lua
  pyroet-os/system/kernel/*.lua    -> /system/kernel/*.lua
  pyroet-os/system/rpv/*.lua       -> /system/rpv/*.lua
  pyroet-os/system/net/*.lua       -> /system/net/*.lua
  pyroet-os/system/system/*.app/** -> /system/system/*.app/**
  pyroet-os/recovery/*.lua         -> /recovery/*.lua
  pyroet-os/ota/*.lua              -> /ota/*.lua   (optional; publisher side only,
                                                      never runs on the pocket)
  pyroet-os/install.set            -> /etc/install.set   (optional)
  pyroet-os/README.md              -> /docs/README.md    (optional)
  pyroet-os/INSTALL.txt            -> /docs/INSTALL.txt  (optional)
  pyroet-os/DECISIONS.md           -> /docs/DECISIONS.md (optional)
  pyroet-os/P6-design.md           -> /docs/P6-design.md (optional)
  LICENSE                          -> /docs/LICENSE      (optional)
Rules: /startup.lua is the only file CraftOS runs; it must load
/system/startup.lua. /apps and /etc are user data. /boot.ok, /boot.tries and
/update.* are runtime state -- never copy them from the archive.

2. GETTING FILES ONTO A POCKET
A pocket cannot mount a disk, so a drive on a desktop is only a step.
A. Rednet push (full image). Type or paste /recovery/proto.lua and
   /recovery/bootstrap.lua (about 28 KB of text; Ctrl+V in the CC editor),
   then run "recovery/bootstrap.lua". A desktop publisher sends
   "PYROET-FLASH/2 PUSH meta ..." plus "PUSH DATA ..." on protocol
   pyroet-flash. The receiver proves every file by SHA-256 and keeps the old
   tree on any failure.
B. Pastebin/wget when the server allows HTTP: fetch the small files, then
   push or type the rest.
C. Manual edit: fine for /startup.lua, /etc/*.conf and one test .app, not for
   a 400 KB image.
Then check: ls /system ; ls /system/kernel ; ls /system/system ; ls /recovery

3. FIRST BOOT
1. reboot. Expect a splash first (logo, "Pyroet OS 0.2.0", a progress bar and the
   step name: checking system / starting services / desktop, ~5 s in total),
   then a first frame like:
     Pyroet OS 0.2.0
     kernel ok
     normal journal none
   The splash is measured by SPLASH_BEGIN / SPLASH_DONE ms=.. in /kernel.log. It
   is skipped on a headless run and when the boot plan is fatal (the FATAL lines
   own the screen instead) -- if you see a logo over a BOOT_FATAL line, the
   startup.lua on the machine is older than the kernel.
2. The desktop then takes the screen: a launcher with the version line, the net
   line, the app list and "<n> apps sel 1/<n>" at the bottom. It stays there and
   the desktop is complete before you touch anything: the app list, the marker
   and the hint row are already on screen at boot (and again right after an app
   exits or a screen loan ends) -- no key press is needed to "wake" it. Then the
   keyboard works: up/down move, a digit selects, enter starts the selected app.
   "q"/"Q"/Esc on the desktop do NOT leave the system: the hint row says
   "Ctrl+T opens power menu" and the list stays. Ctrl+T (the ROM terminate
   event) opens the power menu -- Shutdown / Reboot / Cancel, up/down picks,
   enter runs, Esc or q cancels -- so there is no key that drops you back to
   the CraftOS shell. The menu also has "Update": it lists /pkgs/*.app on
   this computer's own disk (a pocket computer has no disk drive, so that is
   the only local source) and applies a package through the kernel bridge,
   and says "no updates" with a reason when there is nothing to apply (q
   goes back; no Esc needed). Inside an app Ctrl+T leaves that app first (back to the
   desktop); press it again on the desktop to get the menu.
2b. PERMISSION DIALOG (Android style). The first time a user package in /apps
   asks for a capability nobody has decided yet (no line in
   /etc/perms/<app>.cfg), the launcher shows:
     Permission request
     <app> wants <capability>
     [Allow]  [Deny]
   A = Allow (writes "granted"), D = Deny (writes "denied"); any other key does
   nothing (a question cannot be dismissed with q). After the answer the start is
   retried: Allow starts the app with the capability, Deny starts it with that
   capability refused ("capability denied: <cap>" on use). Image packages under
   /system are pre-granted and never ask, and a capability that already has a
   line is never asked about again. Headless boots (loop=false, the offline
   suite) have nobody to ask and keep the old policy. Settings has a
   "permissions" row: enter lists the apps, enter again lists the capabilities
   with granted/denied/ask, enter toggles and writes, q goes back one level.
   Log lines: PERM_ASK app=.. cap=.. and PERM_ANSWER app=.. cap=..
   verdict=allowed|denied by=user.
   If it returns to the shell right away, or if keys do nothing while the screen
   stays put, grep /kernel.log for STARTUP_DESKTOP_SKIP: input_denied /
   terminal_denied means the capability was refused (from the shell run
   permissions.reset("launcher") and reboot), no_module means the image is
   missing /system/kernel/desktop.lua, no_input means the launcher package no
   longer declares "input". A stale /etc/perms/launcher.cfg written by an older
   image is migrated on the next boot: the log shows PERMS_STALE ...
   caps=input,terminal and PERMS_SAVED ... granted=4 denied=0.
   launcher is the desktop itself: it never appears in its own app list, so a
   boot shows only the packages that are actually launchable.
   The three system apps are keyboard-operable (T14): enter on settings /
   installer / net hands them the keyboard and the screen.
     settings   up/down pick a row, left/right/enter cycle its value and
                write that one line of /etc/network.conf (a machine without the
                file gets the two documented defaults and the first change
                creates it), q back
     net        up/down scroll the hosts, enter or r refresh (rpv status,
                hosts, probe target), q back
     appstore   built-in package downloader: a edits the server line, enter
                downloads the selected package into /pkgs and installs it.
                With no /etc/appstore.servers the default server is
                rhtp://store.pyrotechnic.org/ (RHTP/1.0, default port 8080), so a
                fresh machine can install without pressing a first; a still
                overrides it for this session. Typing a bare host[:port]/path is
                read as rhtp://; a http:// address is refused.
                The last row of the list, "System update", is the image update:
                enter reads <base>/meta.txt (base = first line of
                /etc/ota.servers, else rhtp://pyroet.pyrotechnic.org/upgrade),
                shows the remote version, then downloads and applies every file
                with a "fetching <rel> (i/n)" progress row; the result is
                "reboot to apply", and any failure is one readable line with the
                running system untouched.
                Server layout (plain text, any RHTP server: GET <path>, and the
                optional "off=<n> len=<n>" chunk extension answered with 206):
                  index.txt           "app <name> <version> <dir>" per line
                  <dir>/files.txt     one relative path per line
                  <dir>/<relpath>     the file
                  <dir>/SHA256.txt    optional "<sha256> <relpath>" lines;
                                      without it the status says unverified
                l arms the rednet receiver: the status row shows
                "listening ch=4101 id=<computer id>", q stops listening, and
                /etc/appstore.recv may override channel= / protocol=. Another
                computer runs tools/pushpkg.lua (below) to stream a package
                into /pkgs; a failed transfer leaves no .part tree behind.
                t switches the target when /disk exists (a handheld sitting in
                a disk drive of a block computer): the status row reads
                "target self" (/pkgs) or "target disk" (/disk/pkgs). Run appstore
                on the block computer, press t to pick disk and download: the
                package is written to /disk/pkgs/<name>.app and api.sys.install
                is NOT called (a block computer cannot install onto the
                handheld), and the status row ends with "written to disk".
                Take the handheld out and install it there with its installer.
                Without a drive t only says "no disk drive" and the target
                stays self.
      pushpkg    (a copy on the OTHER computer; not part of the image)
                pushpkg [--http] <target-id|broadcast> [name] reads index.txt
                and the package files over RHTP, then streams them to the
                handheld (PYROET-PKG/1, channel 4101 by default).
                /etc/pushpkg.conf: server=<rhtp base>, http=1, protocol=,
                channel= (logged), timeout=. The default server (no config file,
                or no server= line) is rhtp://store.pyrotechnic.org/ .
                RHTP is the default but this tool runs on ANOTHER computer: it
                loads /system/rpv/loader.lua + /system/net/service.lua +
                /system/net/rhtp.lua from the OS installed there and reuses that
                one client. A machine without the rpv stack reports
                "PUSHPKG_FAIL err=no_rhtp reason=.. hint=--http" instead of
                falling back quietly; --http (or http=1) uses the ROM http table
                and is a host-side debugging path only.
                index.txt takes "app <name> <version> <dir>" and
                "lua <name> <version> <file.lua>"; a lua entry is wrapped
                into manifest.lua + main.lua (capabilities
                fs.read,input,terminal) before it is sent. Every message
                waits for an ack (retried twice), and a refused stream is
                aborted so the handheld keeps no half package.
     files      (optional example package) a read-only file manager: up/down,
                enter to open/view, b or backspace up, r refresh, h hidden,
                q quit. Not in the image: copy examples/files.app to /pkgs/files.app
     net        (optional example package, not in the image) copy examples/net.app
                to /pkgs/net.app, then install it from the installer or Update
     web        (optional example package) text browser: default page about:home (built in,
                no network needed), enter opens the address from /etc/browser.home,
                addresses are http(s)://..., local:/path (a file on this computer)
                or about:home; a (or /) edits the address, c cancels editing,
                enter opens, backspace deletes; up/down scroll, b back, r reload,
                q quits (in reading mode only -- while editing q is a letter)
     installer  up/down (or a digit) pick a package, enter installs /
                removes / reports "locked" via the host bridge, c cancels,
                q back. No source shows "no source: checked /pkgs", no bridge
                shows "unavailable" -- it never pretends to install.
   A third-party package that declares no "input" gets a screen that is cleared
   before it is shown (and cleared again before the desktop comes back), so the
   old frame can never mix with the new one.
   loan as usual (visible frame, DESKTOP_LOAN, ends on its own stop, the timer, or
   a hard cap logged as DESKTOP_LOAN_ABORT -- a loan always ends). The desktop owns the console, so from STARTUP_DESKTOP_QUIET on
   the boot log only goes to /kernel.log -- that is normal, not a hang.
3. Check: cat /boot.ok ; tail /kernel.log
   /boot.ok is one line:
     PYROET-BOOT-OK-2 version=0.2.0 manifest_sha=none ts=<ms>
4. "Pyroet OS: cannot load /system/startup.lua" or "startup failed" means the
   image is incomplete or broken: see section 6.

4. MINIMAL CONFIG
/etc/network.conf (key=value, # comment, ip required):
  ip=10.0.0.5
  prefix=24
  gateway=10.0.0.1
  dns=10.0.0.1
There is no iface_side key: the modem is auto-discovered. A stale
iface_side=<side> line is ignored and logged as NET_CONFIG_IGNORED.
dns= is the resolver for name lookups (one IPv4). Omit it and the gateway is
used; dns=0 means "no resolver cache" (the gateway is still the server).
rhtp_secret=<64 hex> turns on PSK sealing for RHTP responses (optional,
default off = plaintext). The handheld and the deployed rhtp_server must share
the SAME 64-hex secret: the client sends Rhtp-Seal: 1 on each request; the
server seals the response body (ChaCha20 + HMAC-SHA256 tag bound to a per
request random nonce and the status line, /system/net/rhtp_secure.lua). The
client rejects a bad tag ("seal bad") and fails closed if the server replies
plaintext to a sealed request ("seal required"). Leaving it unset keeps the
old plaintext behavior but is the insecure default (integrity via SHA-256
only, no authenticity). See DECISIONS.md 45.9.
/etc/hosts.conf ("<hostname> <ipv4>"; static names, checked BEFORE DNS):
  router 10.0.0.1
  server 10.0.0.10
Name lookups (RHTP): node:lookup() (nil in this image), then /etc/hosts.conf,
then a real DNS QUERY: /system/net/dns.lua sends one A question (UDP 53) with
1 s per attempt and 2 attempts, caches positive answers for min(TTL, 60) s and
never caches a failure. /kernel.log shows DNS_QUERY host=.. server=..,
DNS_ANSWER host=.. ip=.. ttl=.., DNS_TIMEOUT / DNS_NXDOMAIN / DNS_BAD_PACKET,
and the RHTP side adds RHTP_RESOLVE host=.. ip=.. source=dns.
The desktop loop pumps the network once per scheduler tick (0.02 s budget), so
an RHTP request made by an app really finishes; look for DESKTOP_PUMP ok=1 n=..
/etc/net.target (Net app probe target, "<ipv4> <port>"):
  10.0.0.10 80
The net service ships but is not registered by the default boot chain in
1.0.0; inject its kernel spec to start it:
  local spec = dofile("/system/net/service.lua").spec({ log = print })
  -- pass { services = { spec } } to /system/startup.lua run(opts)

5. UPDATE AND RECOVERY
System OTA over the network (the normal path, RHTP/1.0), base = first line of
/etc/ota.servers or rhtp://pyroet.pyrotechnic.org/upgrade. The client belongs to
the net service (it owns the one rpv node), so start one first:
  local rpv = dofile("/system/rpv/loader.lua")
  local svc = dofile("/system/net/service.lua").new({ rpv = rpv, peripheral = peripheral })
  svc:start()
  local ota = dofile("/system/kernel/ota.lua").new({
      rhtp = { get = function(u) return svc:rhtp_get(u) end,
               fetch = function(u, s) return svc:rhtp_fetch(u, s) end },
      log = print })
  ota:update() ; print(ota:status().state)
The desktop entry is appstore's "System update" row (enter, then wait for
"reboot to apply"). The server serves the same description as the rednet peer:
  GET <base>/meta.txt   -> PYROET-OTA/2 META version=.. files=.. manifest_sha=..
                           then one "<relpath> <size> <sha256>" line per file
  GET <base>/<relpath>  -> the file body
System OTA over rednet (no network client needed, publisher rednet id 12):
  local ota = dofile("/system/kernel/ota.lua").new({ host = 12, log = print })
  ota:update() ; print(ota:status().state)
Either source verifies the manifest hash and the backup cap BEFORE touching
/system, stages every file, keeps the old bytes in /update.backup until commit,
and rolls itself back on failure. Rescue reflash:
  recovery/flash.lua --disk=/disk/firmware   (from a disk drive)
  recovery/flash.lua --host=12               (from rednet)
  recovery/bootstrap.lua                     (push receiver)
Phases: describe -> stage+prove -> apply. A failed apply undoes itself by
content hash; success writes an "applied" journal so the next boot trial-
boots the image and falls back from /update.backup. User apps only (system
apps change only through OTA):
  local inst = dofile("/system/kernel/installer.lua").new({ log = print })
  inst:install("hello") ; inst:list() ; inst:uninstall("hello")

6. TROUBLESHOOTING
Drops to shell with an ASCII error:
- "cannot load /system/startup.lua": /system missing or unreadable. Re-copy
  the tree, or run recovery/flash.lua from /recovery.
- "startup failed" + reason: check "tail /kernel.log" for the last
  STARTUP_*/BOOT_* line.
Three failed boots: the bootloader rolled back to /update.backup. Look for
BOOT_ROLLBACK*, cat /boot.ok (old version), ls /update.journal.*; then retry
the update or reflash.
"BOOT_ROLLBACK_FAIL" / "FLASH_REQUIRED tool=recovery/flash.lua": the backup
cannot be proven; boot stops on purpose (no reboot loop). Reflash.
"BOOT_FATAL reason=no_system": /system is gone; only a flash restores it.
NET_* / health=degraded: config errors never block boot. Read the NET_* line;
parse errors include the line number. Check modem, ip.
"capability denied: <cap>": /etc/perms/<app>.cfg denies it (or the app is not
a system package). A corrupt decision file denies everything and is never
rewritten; delete it to be asked again.
"permission pending: <cap>" / APP_PERM_PENDING: the desktop is asking you (look
for PERM_ASK and the Permission request dialog). Answer with A or D; if no
dialog appeared, /kernel.log DESKTOP_PERM_REQUEST says whether the request was
delivered -- a launcher without "input"/"terminal" granted cannot draw it.
"PERMS_PREGRANT" never appears for a user package: only image packages under
/system are pre-granted, so a package in /apps always gets the dialog once.
"No such program": run recovery programs by path, e.g.
"recovery/flash.lua --host=12".
Storage: "df" shows free space; keep >= free-space-for-image + 200,000 B free
before an update (the current image is 650,447 B, so about 850,000 B). The
build gate is 10 MiB (2026-11-01), but the medium did not grow: a computer and a
floppy still hold 1,000,000 B each, so the gate can bless an image that will not
fit here. A too-large update is refused before any byte is written. Keep
/recovery on the machine: it is the only rescue path.

Keys note
---------
Escape is not a usable key inside the computer at all:
  - in game, the Minecraft client consumes Esc to close the terminal window, so
    the keystroke never reaches the computer;
  - in CraftOS-PC the ROM keys table has no escape entry, so an Esc press would
    arrive as an unmapped code anyway.
Use q (or Q) wherever this document says "Esc", and Ctrl+T for the power menu.
The apps still accept raw code 256 if some terminal does deliver it.
