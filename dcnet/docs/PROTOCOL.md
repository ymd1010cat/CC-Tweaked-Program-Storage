# dcnet 通信协议（v1）

所有消息都是 Lua table，公共字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `t` | string | 消息类型（见下表） |
| `ver` | number | 协议版本，当前为 `1` |

两条 rednet 协议（即 `rednet.send(target, msg, protocol)` 的第三个参数）：

| 协议 | 用途 | 谁在收 |
| --- | --- | --- |
| `dccomp` | 注册、派任务、回结果、心跳、控制 | 主控一个循环；每个节点一个循环 |
| `dcpush` | 代码分发（拉取 / 推送 `worker.lua`） | 主控一个循环；bootstrap 脚本阻塞收 |

设计约束（CC 特有）：**同一个程序里，同一个协议只能有一个 `rednet.receive`
循环**。CC 的 `parallel` 会把同一个事件分发给所有 filter 匹配的协程，
两个同协议接收循环会把同一条消息处理两次。

## 1. `dccomp`：控制与任务

### 1.1 上线握手

```
节点                                    主控
 │  ── who（广播） ──────────────────────▶   （还没登记，主控直接应答）
 │  ◀──────────────── iam {master=2} ────
 │  ── hello {name, wireless, have} ─────▶   建/更新节点表，打印"已连接"
 │  ◀────────── welcome {master, cfg} ───   节点拿到 pollInterval / taskTimeout
```

- 节点启动时若给了主控 ID 就跳过 `who`/`iam` 直接 `hello`。
- `have` 是节点当前缓存的作业源码哈希，主控据此决定要不要附带源码。

### 1.2 任务循环（拉模型）

```
 │  ── pull {have} ──────────────────────▶   有活：assign() 派一个任务
 │  ◀──── task {job,task,payload,...,src} ─   （src 仅在哈希不匹配时附带）
 │      … 计算中：ctx.tick()/ctx.progress() …
 │  ── progress {job,task,pct,note} ─────▶   刷新任务最后活跃时间
 │  ── result {job,task,ok,data|err,ms} ─▶   记账；全部任务结束则 reduce
```

没有任务可派时主控回 `idle {wait}`，节点等待 `wait` 秒后再 `pull`。

### 1.3 消息表

| `t` | 方向 | 字段 | 说明 |
| --- | --- | --- | --- |
| `who` | 节点 → 广播 | — | 寻找主控 |
| `iam` | 主控 → 节点 | `master`, `version` | 应答 `who` |
| `hello` | 节点 → 主控 | `name`, `wireless`, `have` | 登记/重连（幂等） |
| `welcome` | 主控 → 节点 | `master`, `cfg{pollInterval,taskTimeout}` | 握手完成 |
| `pull` | 节点 → 主控 | `have` | 要任务；同时是心跳 |
| `idle` | 主控 → 节点 | `wait` | 暂时没活 |
| `task` | 主控 → 节点 | `job`, `task`, `name`, `hash`, `payload`, `timeout`, `tries`, 可选 `src` | 派发任务 |
| `progress` | 节点 → 主控 | `job`, `task`, `pct`, `note` | 进度（节流 ~0.7s） |
| `result` | 节点 → 主控 | `job`, `task`, `ok`, `data` 或 `err`, `ms` | 任务结果 |
| `cancel` | 主控 → 节点 | `job`, `task` | 任务已被重派，请放弃（节点在下次 `ctx.tick()` 生效） |
| `halt` | 主控 → 节点 | 可选 `reboot=true` / `shutdown=true` | 节点退出；`reboot` 调 `os.reboot()`，`shutdown` 调 `os.shutdown()` 关机（配合 `push` 加载新代码） |
| `ping` / `pong` | 双向 | — | 保活探测（可选） |
| `bye` | 节点 → 主控 | `reason` | 主动下线 |
| `screen` | 屏幕 → 广播 | `name`, `w`, `h`, `scale` | 网络屏幕上线登记 + 心跳（缺省每 3s） |
| `screenbye` | 屏幕 → 主控 | `reason` | 屏幕主动退出 |
| `disp` | 主控 → 屏幕 | `master`, `w`, `h`, `lines`（`textutils.serialize` 后的字符串）, `at` | 一帧面板内容（缺省每 1s） |
| `screenoff` | 主控 → 屏幕 | `why` = `off` / `full` / `ver` / `kick` | 推送已关闭 / 屏幕数满 / 版本不符 / 被踢 |

### 1.4 超时与重派

| 判据 | 默认 | 结果 |
| --- | --- | --- |
| 节点距上次任何消息 | > `workerTimeout`（12s） | 节点标记离线；其手中的运行中任务重新入队 |
| 任务距上次 `progress` | > `taskTimeout`（90s） | 任务重新入队（**有进度就自动顺延**，长任务不会被误杀） |
| 任务被派发次数 | > `maxTries`（3） | 任务标记失败，日志记录原因，作业继续 |

重派时主控会向原节点发 `cancel`；取消是**协作式**的，节点上的 `map`
需要在热循环里调用 `ctx.tick()` 并检查 `ctx.canceled()` 才能及时退出。

迟到的 `result` 会被忽略（任务已完成/已失败时不再计数），因此重复计算不会
污染汇总结果。

## 1.5 网络屏幕（`screen` / `disp`）

用途：显示器贴在**另一台电脑**侧面时，主控看不到这个外设。那台电脑运行
`screen.lua` 当「屏幕节点」，只负责把主控推来的面板内容画出来（不参与计算）。

```
屏幕节点                                      主控（在岗）
  │ ── screen {name,w,h,scale}（广播）──────▶   登记 / 刷新尺寸
  │ ◀──────────────── disp {lines,w,h} ──────  一帧面板（缺省每 1s）
  │ ── screen（心跳，缺省每 3s）────────────▶   超过 15s 没消息就摘掉
  │ ◀─────────────── screenoff {why} ───────   关闭推送 / 满了 / 被踢
```

- `screen` 是**广播**：同一网段有几台主控时，只有在岗（active）的那台应答；
  待命主控静默。主控掉线/接管后，屏幕在下一次心跳（≤3s）自动连上新主控。
- 主控只在自己的面板状态变化时也照常每秒推一帧——帧很小（十来行文字），
  重复推送就是它的可靠性保障；屏幕端收到就整屏重绘。
- `lines` 是 `textutils.serialize` 后的字符串（反序列化后是
  `{ text = "一行文本", colour = 颜色码 }` 的数组），由主控按**这块屏幕自己的
  `w`/`h`** 生成（小屏幕自动退化成极简模式）。设了密钥时整帧不直接参与 HMAC，
  签名里只放它的校验和（同 `d`/`src` 的取舍，见 §3）。
- 屏幕不进入 `workers` 表、不参与调度；主控最多同时接 `SCREEN_MAX=16` 块。
- 设了共享密钥时，`screen`/`disp` 和其它 `dccomp` 消息一样要签名/验签；
  屏幕电脑上也要配同一个 `dcnet.key`。

## 2. `dcpush`：分块可靠传输

用于把 `worker.lua`（几万字节）从主控送到新节点。有线网络本身可靠，
但仍用"停等 + 重传 + 结束校验"处理对端重启等情况。

```
发送端                                          接收端
 put   {xid,name,i,n,d}  ─────────────────────▶  暂存分块
                         ◀─────────────────────  putack {xid,i}
 put   {xid,i+1,...}     ─────────────────────▶  …
 putdone {xid,n}         ─────────────────────▶  检查 1..n 是否齐全
                          齐全 → 组装落盘
                         ◀─────────────────────  putok {xid}
                          缺失 → 
                         ◀─────────────────────  putmiss {xid,miss={…}}
 put（重传缺失块）
 putdone                 ─────────────────────▶  …
```

| `t` | 方向 | 字段 |
| --- | --- | --- |
| `fetch` | 请求方 → 主控 | `xid`, `what`（`"worker"`） |
| `put` | 发送端 → 接收端 | `xid`, `name`, `what`, `i`, `n`, `d`（分块内容） |
| `putack` | 接收端 → 发送端 | `xid`, `i` |
| `putdone` | 发送端 → 接收端 | `xid`, `n` |
| `putmiss` | 接收端 → 发送端 | `xid`, `miss`（缺失下标数组） |
| `putok` | 接收端 → 发送端 | `xid` |
| `referr` | 主控 → 请求方 | `xid`, `err`（主控上没有该文件） |

参数（见 `src/lib/xfer.lua`）：

| 参数 | 值 | 说明 |
| --- | --- | --- |
| `CHUNK` | 4096 字节 | 每个分块大小（留足余量，避免 modem 消息过大） |
| `ACK_TIMEOUT` | 4 秒 | 等一个确认的上限，超时重传该块 |
| `MAX_TRIES` | 6 | 单块最多重传次数 |
| `RECV_IDLE` | 45 秒 | 接收端半成品超时丢弃 |

`xid` 由 `电脑ID-序号-随机数-标签` 组成，主控可以同时处理多个推送
（多个新节点一起 bootstrap 不会串台）。

## 3. 消息签名与防重放（可选）

设置共享密钥后（主控 `setkey <密钥>`、节点 `set dcnet.key <密钥>`），每条消息都带：

| 字段 | 含义 |
| --- | --- |
| `sid` | 会话号：进程启动时随机生成（`crypto.randomHex(8)`），重启即变 |
| `seq` | 会话内单调递增的序号 |
| `ts` | 发送时刻（`os.epoch("utc")`，毫秒） |
| `sig` | `HMAC-SHA256(key, canonical(消息去 sig、大块字段换成校验和))`，十六进制 |

接收端按固定顺序校验，任何一步失败都**丢弃整条消息**并计数：

1. 四个字段缺任何一个 → 未签名；
2. `|now - ts| > 120 秒` → 时间戳无效；
3. 重新计算 HMAC 并定长比较 → 签名错误；
4. 同一 `sid` 的 `seq` 必须**严格递增**，否则算重复（防重放）。

**为什么把大块字段换成校验和**：`d`（分块传输的数据块）、`src`（下发的作业源码）与
`lines`（网络屏幕的一帧）动辄几 KB，游戏内电脑算 SHA-256 要一秒左右，所以签名里只放
它们的 64 位校验和（`dck`/`sck`/`lck`，外加长度 `dlen`/`srclen`/`lineslen`）。
它们的真实性另有保障：作业源码在节点上会用 `util.hash` 与主控声明的哈希比对，
`worker.lua` 的推送也有完整性检查；屏幕帧的内容由主控按自己的状态生成。

`canonical()` 把表按键名排序后序列化，保证同一内容在两台机器上得到同一串字节——
不能直接用 `textutils.serialize`，Lua 的表遍历顺序不保证一致。

未设密钥时完全跳过这些步骤（`net.sign`/`net.verify` 直接放行），协议向后兼容。

## 4. 大负载：引用式负载与结果

任务消息里的 `payload` 与结果消息里的 `data` 超过阈值（主控 `inlineLimit`，默认 8192）
时，改走文件通道，消息里只带名字：

| 方向 | 消息字段 | 池子文件 | 谁发起传输 |
| --- | --- | --- | --- |
| 主控 → 节点（负载） | `payloadRef` | `task-<作业>-<任务>.dat` | 节点发 `FETCH what="taskdata"`（**拉**） |
| 节点 → 主控（结果） | `dataRef` | `res-<作业>-<任务>.dat` | 节点推给主控（**推**） |

- 池子目录 `/dccomp/pool/`，文件名白名单：`task-*.dat`、`res-*.dat`；
  接收端**按名字决定落盘位置**，其他名字（如 `../x.dat`、`worker.lua`）一律拒绝。
- 结果方向是"先推文件、再发只带名字的结果"，所以主控处理 `dataRef` 时文件一定已在
  （读不到就按任务失败处理，不会静默算成功）。
- 结果推送失败（超时）会**退回内联**，不会因为通道故障丢任务。
- 池子里超过 `POOL_TTL`（15 分钟）没被动过的文件由主控 tick 循环清掉。

> **实现约束（重要）**：一个程序里只能有**一个** `rednet.receive("dcpush")` 循环。
> 发送端不自己收确认帧，而是登记进 `xfer.newRegistry()`，由那个唯一循环每次迭代调
> `xfer.pollRegistry()` 推进；阻塞等待用 `xfer.waitFor()`（内部 `os.pullEvent()` 无过滤，
> 依赖 CC 的 parallel "同一事件分发给所有协程"的特性，所以不会抢别人的事件）。
> 早期主控的接收端漏处理 `PUTDONE`、以及两个循环互相抢消息，都是这条规则被破坏导致的。

## 5. 源码下发

作业源码随 `task` 消息的 `src` 字段下发（纯文本），节点用
`loadstring`/`load` 在沙箱环境里编译执行。主控按哈希做缓存协商：

1. 节点每个 `pull` 都带 `have`（最近一次使用过的作业源码哈希）。
2. 主控发现 `have ≠ 当前作业哈希` → 这一条 `task` 附带 `src`。
3. 节点收到后缓存（最多保留 3 份），后续任务不再传输源码。

因此同一作业的绝大多数任务只有几十字节的消息体。作业源码建议 < 8KB
（超过时主控会打印提示）。

## 6. 版本与兼容

- `ver` 不匹配时双方行为未定义；升级时请同时替换主控与节点。
- 新增消息类型是向后兼容的：未知 `t` 会被 `proto.valid()` 判为无关消息而忽略
  （`sched:onMessage` / `worker` 的接收循环只在匹配时采取动作）。
- `dcpush` 与 `dccomp` 相互独立，只升级节点代码时不会影响正在跑的作业。
