# 性能基线与任务粒度

这一页回答两个问题：**一个任务算多久合适**，以及**怎么自己量**。

> 前提（很重要）：下面表格是在 **CraftOS-PC** 上量的——它跑在 PC 的 CPU 上，比游戏里
> 那台"电脑"快**几十倍**。所以表格的意义是**相对关系**（哪个作业什么规模贵多少），
> 绝对值请在目标环境自己量（方法见文末）。

## 怎么用这些数字

**任务粒度的经验法则**：单任务在**游戏内**跑 0.5 ~ 5 秒最合适。

- 太碎（< 0.2s）：网络往返、派发、结果回收的开销占比过高，节点大部分时间在等指令；
- 太粗（> 30s）：抢尾冗余（`redun`）没机会生效，一个节点掉线就得重算很久，
  而且断点续算的粒度太粗（快照里未完成的任务要整块重算）。

换算方法：把游戏内实测的一次 `run` 总耗时除以任务数（看 `status`），就是单任务耗时；
把 chunk / rows / step / body 这类"每任务规模"参数调一调，让它落到 0.5~5 秒。

**几个作业的调节旋钮**：

| 作业 | 粒度旋钮 | 说明 |
| --- | --- | --- |
| `primes` | `chunk` | 每个任务的整数区间长度，直接决定耗时 |
| `pi` | `chunk` | 每个任务的采样数 |
| `matmul` | `rows` | 每个任务算几行；总代价 ∝ n³，行数只按比例切分 |
| `nbody` | `step` | 每个任务算几个天体；总代价 ∝ n² |
| `hashsearch` | `chunk` | 区间长度；命中会提前结束，所以最后几个任务会明显快 |
| `bigdata` | `tasks` / `size` / `res` | 测大负载通道用；耗时主要是序列化与传输，不是计算 |
| `selftest` | `tasks` / `size` | 集群自检用，`size` 决定每个任务的热循环长度 |

**和调度参数的关系**：

- `taskTimeout`（默认 90s）是**初始**预算；开了 `adaptiveTimeout` 后会按 EWMA 收紧，
  下限 `taskTimeoutMin`（15s）。所以任务别做得比 15 秒还慢，否则容易被误判超时重派。
- 走文件通道的大负载任务，预算里会自动加上传输余量（见 PROTOCOL.md）。
- 节点越多、任务越碎，`pollInterval`（默认 1.5s）和抢尾冗余 `redun` 的价值越大。

## 自己量

**在游戏里**（最真实）：

```
run primes to=2000000 chunk=25000
status                # 看任务数与总耗时 → 相除得到单任务耗时
set verbose true      # 打开后每次派发都会打一行，能看到重派/抢尾
top                   # 看各节点的累计贡献与平均耗时，节点强弱一目了然
```

**在 CraftOS-PC 里**（快，适合调参回归）：

```
python tools/bench.py            # 打印表格
python tools/bench.py --write    # 刷新本页表格
```

`tests/bench.lua` 直接调用各作业的 `map`，只量**一个任务**的时间——这就是节点实际
感受到的粒度。想量别的规模，改 `tests/bench.lua` 里的参数即可。

**网段开销**：任务派发与结果回收各是一次 rednet 往返；有线网络下通常几十毫秒，
远小于 0.5 秒的任务时长。真正需要留意的是**大负载走文件通道**的情形——那时
传输时间可能超过计算时间（这也是签名的分块校验和设计存在的原因）。
